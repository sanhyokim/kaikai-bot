# 決めたことと理由(実装役)

仕様書に書いていないことで、実装役が「シンプルで確実」な方を選んだ記録です。仕様書と食い違うものは無く、食い違いそうな点は最後の「提案・確認待ち」に分けています。

## 段階1

### 指標の細かい決まりは広く使われる計算ライブラリ(TA-Lib)に合わせた
仕様書は「標準の計算」としか書いていない部分があるため、試験の照合相手と同じ決まりにした。本体は TA-Lib を使わず自前で計算し、試験の既知の値だけ TA-Lib で作った(tests/make_known_values.py)。
- 指数移動平均の最初の値は、先頭 n 本の単純平均。
- ATR の真の値幅は前の終値が要るので2本目から。最初の ATR は2本目〜15本目の単純平均。
- パラボリックの始まりの向きは、2本目の高値・安値の動きで決める。足が SAR に触れたら(等号でも)反転する。反転した足の SAR は、その足と1本前の足の値幅の外側に置く。

### 収集は確定した足だけ保存する
取得の入口は作りかけの足も返すが、検証で使うのは閉じた足だけなので、保存しない。後から確定値で上書きする仕組み(仕様書 5.2)はそのまま。

### 初回の収集は取れるだけ取る
保存庫が空の時は「最新の1時間前」が無いので、取得できる最も古い足から取る。

### 米国株3銘柄も今日から収集する
仕様書では収集の追加は段階5だが、過去は約3.6日分しか取れず、待つとその分のデータが永久に失われる。収集だけなら取引に影響しないので、最初から設定ファイルの全6銘柄を集める。判定表への追加は仕様書どおり段階5で行う。

### 設定の読み込み用に小さなファイルを1つ足した
`kaikai_bot/config.py`。設定ファイルとデータの置き場所を1か所で読むためだけのもので、売買判断は書かない。

### 収集の状態と警告の置き場所
状態(銘柄ごとの最終取得時刻・連続失敗回数)は `logs/collect_status.json`、警告は `logs/alerts.log`。監視画面はこの2つを読む。

### 除外日の判定は UTC の1日 1440本を基準にする
データの最初の日・最後の日のように途中から始まる日も、1440本の95%に届かなければ除外する。検証に使う日はすべて丸1日そろった日になる。

### 指標は欠損をまたいで計算する
欠損のたびに計算し直すと、毎回長い計算不能期間(長い移動平均は75本+10本)ができる。仕様書 5.4 の「欠損明け10本は入らない」「欠損の直前で手仕舞い」で取引は欠損をまたがないので、指標は残った足を順につないで計算する。

### 米国の休日表は 2026年・2027年
NYSE 公式の休日表から転記。過去データを補う場合は、その年を足す。13時の短縮取引日は仕様書に扱いが無いので記録だけして使っていない。

## 段階2

### 1設定ずつ独立に検証する
7.5 の「持ち玉は全銘柄合わせて1つ」は、1設定=1銘柄・1つの足の検証では他の設定と関係しない。各設定の中で持ち玉は1つまで。

### 1つ上の足は「確定済みの直前の足」を使う
足 t の確定時刻までに閉じた上の足のうち最新のもの。それが直前の区間の足でない(欠けている)時は、環境フィルタを満たさない扱い。先の値を覗かないため。

### 約定した足では利確を見ない
約定した足の高値が約定の前か後か分からないので、保守的に損切りだけを見る。

### 保有本数は約定した足を1本目と数える
1分足の時間切れ15本なら、約定した足から数えて15本目の終値で手仕舞い。

### 出口の順番
損切り → 利確 → 出口方式B → 時間切れ → 強制手仕舞い(欠損の直前・米国株の引け前)。B・時間切れ・強制はどれも終値の taker なので、重なった時は名前だけの違い。

### 手仕舞った足の確定時から次の判断ができる
「持ち玉がある間は判断しない」の終わりを、手仕舞った足が閉じた瞬間とした。

### 安全装置の数え方
- 判断の日は、足の確定時刻の UTC の日。
- 1日の損失は、その日に手仕舞った取引の純損益の合計(勝ちと相殺)が資金の −3% 以下になったら停止。
- 連敗は純損益がマイナスの取引。5連敗した日の UTC 24時まで停止し、明けたら数え直す。

### 前半と後半の分け方
指値を出す時刻(足 t の確定時刻)で分ける。前半の終わりに持っていた玉は、後半に入っても手仕舞いまで追う。後半は安全装置の状態を空にして始める。

### データの終わりで持ち玉が残った取引は数えない
結果が出ていないため。

### パラメータ探索の比べ方
前半の PF が最も高い組。同じなら取引回数が多い組、それも同じなら探索表の先の組。取引0回の組は比べない。負けが0回の組は PF を無限大とする(仕様書の「PF で選ぶ」どおり)。全組が0回なら初期値を使う。

### 判定の順番と、データ待ちの行の数字
後半90日未満 → データ待ち、後半300回未満 → 判定不能、そのほか7基準。データ待ちの行も、仕組みの確認のため前半で選んだパラメータと数字は表に出す(判定には使わない)。

### 基準5で総利益が0以下の時
「最も儲かった月 ÷ 総利益」が計算できないので、満たさない扱い。

### 基準7で隣の足がデータ待ちの時
判定不能と同じく基準7を適用しない。

### 米国株の時間帯
- 指値を出す時刻(足 t の確定時刻)が NY 9:50 以上 15:30 未満で、土日・休日でない時だけ入る。
- 約定を見る次の足の終わりが 15:55 を過ぎるなら入らない(1時間足なら 15:00 確定の合図は見送り)。
- 持ち玉は、次の足の終わりが 15:55 を過ぎる足の終値で手仕舞う。

### 資金調達料の保有時間
約定した足の始まりから、手仕舞った足の終わりまで。

### 時間帯別成績
後半の取引を、約定した足の始まり(UTC の時)で分ける。

### 否決メモの所見
「取引回数不足」「コスト負け(コスト前は PF 1.0以上)」「ロジック負け(コスト前から PF 1.0未満)」「その他の基準」の決まった文から選ぶ。推測は書かない。

### 結合試験の入り口の合図は人工的に置いた
13.2 の「入る→利確/損切り/時間切れ」は、指標6条件を人工の値段でそろえるのが難しいため、合図の位置を直接与え、約定・出口・コストの計算を手計算と照合した。指標と条件の判定はそれぞれの単体試験で確かめている。

### 判定表の CSV は BOM 付き UTF-8
Excel で開いた時に文字化けしないため。

## ボスが決めた仕様書からの変更(Commander に版上げを依頼する)

### 収集は GitHub の自動実行で1時間ごとに動かす(2026-10-25 ボス決定)
- 仕様書 5.5 は「cron か Windows タスクスケジューラ」。ボスのパソコンが3日以上止まるとデータが永久に欠けるため、GitHub の自動実行(`.github/workflows/collect.yml`)で動かす。
- 貯め方: リポジトリの `data` 枝に `candles/<銘柄>/<UTC日付>.csv`。銘柄名の「:」は「_」に置き換え(xyz:NVDA → xyz_NVDA)。欠損の記録 `gaps.log` と状態 `collect_status.json` も同じ枝に置く。
- パソコンでは `python -m kaikai_bot.collect --from-github` で `data/market.db` に取り込む。保存の形(5.2 の表)は変えていない。
- 版上げの文案(5.5 の1行目の差し替え): 「`python -m kaikai_bot.collect --store <保管庫>` を GitHub の自動実行で1時間に1回動かし、data 枝に日ごとのファイルで貯める。パソコンでは `--from-github` で取り込む。」

### 過去データの保管庫(公式の約定記録)は今は使わない(2026-10-25 ボス決定)
AWS 契約が要るため見送り。判定は毎日の収集で約225日分が貯まってから。

## 提案・確認待ち

- キリのいい数字の定義: 例(BTC 68,000、NVDA 190)と合う「上から3桁目以降が0の数」で実装。SOL の「50刻み」はこの中に含まれる。
- 未来の値動きで先に24設定の紙上運転を始めるか(ボスの決定待ち)。
- 入り口の条件がほとんどそろわない(2026-10-25 時点の約3.6日分で24設定とも合図0回、試しの作り物の値動き225日分でも1分足で数回)。トレンド条件(移動平均が上向き)と、RCI中期 −50以下・マイナス圏のゴールデンクロス(直前の下げの印)がぶつかるため。このままでは後半300回に届かず全設定が判定不能になる恐れ。ルールの見直しは Commander の版上げ事項。
