## 1. 目的と「勝ち」の定義

### 1.1 目的

X(旧Twitter)の投資家 kaikai 氏が公開した日本株1分足のスキャルピング手法(以下「元手法」)を、人の勘に頼らない機械のルールに書き直し、Hyperliquid の暗号資産と米国株の永久先物で**本当に利益が出るかを数字で判定し**、出るならそのルールで自動売買する。

### 1.2 「勝ち」の定義(優先順)

1. **第1の勝ち**: 検証(過去データで試すこと)で合格する設定(足×銘柄×パラメータ)が1つ以上見つかり、紙上運転(注文を出さずに本番の値動きで動かすこと)でも合格し、少額本番で**手数料と資金調達料を引いた後の純利益がプラス**で4週間終わること。
2. **第2の勝ち**: 全設定が不合格になり、「なぜ負けるか」が否決メモとして数字で残ること。これも勝ちです。勘でやって負けるより価値があります。
3. **負け**: 判定ができない状態(データ不足・バグ・基準の後出し変更)で終わること。これだけが負けです。

### 1.3 やらないこと

- 元手法のうち機械化できない部分(板読み、キリのいい数字の攻防戦、ローソク足の形、ゴールデンクロスの「綺麗さ」)は**最初から捨てる**。後から足さない。
- ショート(売りから入る取引)は第1版ではやらない。ロング(買いから入る取引)のみ。
- 数秒で手仕舞うスキャルピングはやらない。保有は数分〜数時間。
- bot-factory との連携(自動・手動とも)は作らない。

## 2. 用語集(この文書で使う言葉)

| 言葉 | 意味 |
|---|---|
| 足 | 一定時間の値動きを1本にまとめたもの。1分足=1分ごと、5分足=5分ごと |
| 本 | 足の数え方。「10本前」=10本前の足 |
| 永久先物 | 期限のない先物取引。Hyperliquid の商品はすべてこれ |
| HIP-3 | Hyperliquid 上で第三者業者が自分の市場を作れる仕組み。米国株の永久先物はこれで提供されている。業者名 xyz(trade.xyz)の市場は「xyz:NVDA」のように書く |
| 検証 | 過去データでルールを動かして損益を計算すること(バックテスト) |
| 紙上運転 | 本番の値動きでルールをリアルタイムに動かすが、注文は出さず記録だけすること(paper trading) |
| 少額本番 | 実際に注文を出す運用。資金はボスが決めた少額 |
| 設定 | 足・銘柄・パラメータの組み合わせ1つ。検証の単位 |
| 判定表 | 設定ごとの成績を並べた表 |
| 否決メモ | 不合格になった設定について「なぜ負けたか」を書いた記録 |
| 指値 | この値段でだけ売買する注文 |
| 逆指値 | この値段に達したら発動する注文。損切りに使う |
| 滑り | 思った値段と実際の約定値段の差 |
| 資金調達料 | 永久先物で保有中に定期的に払う(または受け取る)お金。Hyperliquid では1時間ごと |
| 米国市場時間 | ニューヨーク時間 9:30〜16:00(夏時間なら日本時間 22:30〜翌5:00、冬時間なら 23:30〜翌6:00) |
| 前半/後半 | 検証データを時間で分けたもの。前半でパラメータを決め、後半でそのまま確認する |

## 3. 全体像

### 3.1 工程(左から右へ流れる)

```
データ収集 → 指標計算 → 検証 → 判定表・否決メモ → 紙上運転 → 少額本番 → 監視
```

### 3.2 段階(作る順番)

| 段階 | 作るもの | 完了の条件 |
|---|---|---|
| 1 | データ収集・保存・上位足の生成・指標計算 | 3銘柄の1分足が毎日自動で貯まり、指標の単体試験が全部通る |
| 2 | 検証エンジン・判定表・否決メモ | 12設定(足4×銘柄3)×出口方式2の判定表が1コマンドで出る |
| 3 | 紙上運転・監視画面 | 合格設定(なければ暫定設定)が24時間動き続け、画面で見える |
| 4 | 少額本番 | ボスの指示で開始。鍵と資金の用意を待つ(ここだけ停止点) |
| 5 | 米国株(HIP-3)への展開 | 段階2の判定表に米国株3銘柄が加わる |

段階5は段階2の後、段階3と並行で進めてよい(データが貯まり次第)。

### 3.3 実装役の進め方

- 段階1→2→3は、ボスや Commander の合図を待たず、完了条件を満たしたら自分で次に進む。各段階の終わりに報告だけ出す。
- 段階4だけは、ボスが鍵と資金を用意するまで着手しない。
- 試験の軽い不備(引数の渡し忘れ、試験用データの不足など、期待値・製品コード・既存試験を変えずに直せるもの)は、止まらずに自力で直して進む。
- この文書に書いていないことで判断に迷ったら、「シンプルで確実」な方を選び、報告に「ここは自分で決めた」と書く。推測・しきい値・設定項目を勝手に増やさない。

## 5. データ

### 5.1 取得元

- Hyperliquid の公開 API(情報取得用の入口 `https://api.hyperliquid.xyz/info`)。鍵は不要。
- 要求の種類は `candleSnapshot`(足の取得)。銘柄・足の種類(`1m`)・開始時刻・終了時刻を指定する。
- 1回の要求で取れる本数に上限がある(目安 5000本)。上限を超える期間は要求を分割する。
- 取得できる過去の範囲には限りがある。**そのため、毎日自動で取得して自分の保存庫に貯める**。これが長期の検証データの唯一の出どころになる。
- 実装役は段階1の最初に「今の時点で過去何日分の1分足が取れるか」を3銘柄で調べて報告する。

### 5.2 保存形式

- SQLite 1ファイル(`data/market.db`)。理由: 1台で動かす前提、依存が少ない、壊れにくい。
- 表 `candles_1m`

| 列 | 型 | 意味 |
|---|---|---|
| coin | 文字 | 銘柄コード(例 `BTC`、`xyz:NVDA`) |
| ts_open | 整数 | 足の開始時刻(UTC、ミリ秒) |
| open | 実数 | 始値 |
| high | 実数 | 高値 |
| low | 実数 | 安値 |
| close | 実数 | 終値 |
| volume | 実数 | 出来高 |
| trades | 整数 | 約定回数(API が返す場合) |
| fetched_at | 整数 | 取得した時刻(UTC、ミリ秒) |

- 主キー: (coin, ts_open)。同じ足を二度取ったら上書き(API の値が後から確定することがあるため)。
- 1分足だけを保存する。5分・15分・1時間足は保存せず、必要な時に1分足から計算で作る(5.3)。

### 5.3 上位足の生成規則

| 足 | 作り方 |
|---|---|
| 5分足 | UTC で 分が 0,5,10,…,55 から始まる5本の1分足をまとめる |
| 15分足 | UTC で 分が 0,15,30,45 から始まる15本をまとめる |
| 1時間足 | UTC で 分が 0 から始まる60本をまとめる |

- まとめ方: 始値=最初の1分足の始値、高値=最大、安値=最小、終値=最後の終値、出来高=合計。
- 1分足が1本でも欠けている区間の上位足は**作らない**(欠損扱い)。穴埋めや補間はしない。

### 5.4 欠損の扱い

- 欠損区間(API が返さない、取得失敗)は `data/gaps.log` に銘柄・開始・終了を記録する。
- 検証では欠損区間をまたぐ取引は発生させない(欠損の直前で持ち玉を終値で強制手仕舞いし、欠損明け10本は新規に入らない)。
- 1日の欠損が全体の5%を超える日は、その日を検証から除外し、判定表の備考に除外日数を書く。

### 5.5 収集の運転

- `python -m kaikai_bot.collect` を1時間に1回、定時実行(cron か Windows タスクスケジューラ。実装役が動かす環境に合わせる)。
- 毎回「保存庫の最新時刻の1時間前」から現在までを取り直す(重複は上書き)。
- 失敗したら次回に自動で取り直す。3回連続失敗で監視画面に警告を出す。

### 5.6 コストの設定値(設定ファイル `config/costs.yaml`)

実装役は段階1で Hyperliquid の公式文書から現在の手数料を確認し、下の初期値を上書きする。確認日を設定ファイルに書く。

| 項目 | 初期値 | 意味 |
|---|---|---|
| taker_fee | 0.045% | 板を取りに行く注文(成行や、すぐ約定する指値)の手数料 |
| maker_fee | 0.015% | 板に置いて待つ注文の手数料 |
| hip3_fee_multiplier | 2.0 | HIP-3 銘柄は手数料をこの倍にする |
| slippage_stop | 0.02% | 損切り(逆指値→成行)にかかる滑り |
| slippage_entry | 0.00% | 入り口は指値なので滑りなし(約定しなければ見送るだけ) |
| funding_per_hour | 0.001% | 保有1時間あたりの資金調達料(平均の見積もり)。保有時間に比例して引く |

- 検証では**入り口 maker、利確 maker、損切り taker+滑り**として計算する。
- これらは「保守的(損益を悪く見積もる)」に設定する。実際より有利な数字は使わない。

## 6. 指標の定義(計算式)

すべて終値ベース。`t` は現在の足、`t-1` は1本前。計算に必要な本数が足りない期間は「計算不能」とし、その足では売買判断をしない。

### 6.1 単純移動平均線 SMA(n)

直近 n 本の終値の平均。n = 5, 25, 75 の3本。

**上向きの定義**: `SMA(n)[t] > SMA(n)[t-10]`(10本前より高い)。
**下向きの定義**: `SMA(n)[t] < SMA(n)[t-10]`。

### 6.2 パラボリック SAR

標準の計算(Wilder 方式)。加速因子の初期値 0.02、増分 0.02、上限 0.20。
- **陽**: SAR の値が足の安値より下にある(点が足の下)。
- **陰**: SAR の値が足の高値より上にある。
- 陽転: 前の足が陰で今の足が陽になること。

### 6.3 MACD(12, 26, 9)

- MACD線 = EMA(12) − EMA(26)(EMA=指数移動平均)
- シグナル線 = MACD線の EMA(9)
- **ゴールデンクロス**: `MACD[t-1] <= シグナル[t-1]` かつ `MACD[t] > シグナル[t]`
- **マイナス圏でのゴールデンクロス**: ゴールデンクロスが起き、かつ `MACD[t] < 0`

### 6.4 RCI(n)(順位相関指数)

直近 n 本について、時間の順位(新しいほど大きい)と終値の順位(高いほど大きい)の差 d を各足で求め、

```
RCI(n) = (1 − 6 × Σ(d²) / (n × (n² − 1))) × 100
```

範囲は −100〜+100。n = 9(短期)と 14(中期)。
同じ終値が複数ある時の順位は平均順位(例: 2位と3位が同値なら両方 2.5)。

**傾き**: `slope9[t] = RCI(9)[t] − RCI(9)[t-1]`。
**急角度**: `slope9[t] >= rci_slope_min`(パラメータ。初期値 20)。
**上向きに転じた**: `RCI(14)[t] > RCI(14)[t-1]` かつ `RCI(14)[t-1] <= RCI(14)[t-2]`。

### 6.5 ATR(14)

真の値幅 TR = max(高値−安値, |高値−前終値|, |安値−前終値|)。ATR はその Wilder 平均(14本)。
値段の単位で出る。損切り・利確の幅に使う。

### 6.6 指標の単体試験(段階1の完了条件)

- 各指標について、既知の値(例: 手計算した20本分の表、または定評ある計算ライブラリの結果)と小数点以下4桁で一致することを試験で確かめる。
- RCI は同値がある場合の順位処理も試験に含める。
- パラボリックは陽→陰→陽の切り替わり本数が既知の表と一致することを確かめる。

## 7. 戦略ロジック v1(ロングのみ)

### 7.1 全体の考え方

元手法の指標5つ(パラボリック・RCI・MACD・移動平均線・ローソク足)のうち、計算式で書ける4つを**すべて同時に満たした時だけ**買う。出口は入る前に3つ決めておく。これだけです。判断は毎足の**確定時**(足が閉じた瞬間)に1回だけ行う。足の途中では何もしない。

### 7.2 時間帯フィルタ

| 対象 | 入ってよい時間 |
|---|---|
| 仮想通貨 | 24時間(フィルタなし)。ただし判定表には「入った時刻(UTC の時間帯 0〜23)」を記録し、時間帯別の成績を別表で出す |
| 米国株(HIP-3) | ニューヨーク時間 9:50〜15:30 のみ。9:30〜9:50 は元手法の「寄付直後は指標が効かない」に従い除外。15:30 以降は新規に入らない。持ち玉は 15:55 までに終値で強制手仕舞い |

- 夏時間・冬時間の切り替えは `America/New_York` の時刻計算ライブラリに任せる。自前で時差を決め打ちしない。
- 米国の祝日(市場が休みの日)は入らない。祝日表は設定ファイル `config/us_holidays.yaml` に年ごとに書く(実装役が公式の取引所カレンダーから転記し、出典と確認日を書く)。

### 7.3 環境フィルタ(トレンド中かどうか)

次の2つを両方満たす時だけ、入り口の判定に進む。

1. この足での `SMA(25)` が上向き(6.1 の定義)
2. **1つ上の足**での `SMA(25)` が上向き。上の足の対応は 1分→5分、5分→15分、15分→1時間、1時間→4時間(4時間足は1分足から作る。5.3 と同じ要領で UTC 0,4,8,12,16,20 時から始まる)

元手法の「横ばいではパラボリックが向かない」を「横ばいでは入らない」に置き換えたもの。

### 7.4 入り口の条件(6つすべて)

足 t が確定した時点で、次を**すべて**満たすこと。

| # | 条件 | 元手法との対応 |
|---|---|---|
| 1 | パラボリックが陽 | 「パラボ陽の時のみロング」 |
| 2 | 直近 `macd_lookback` 本以内(初期値 3、t を含む)にマイナス圏でのゴールデンクロスが起きた | 「マイナス圏でのGCはかなりの買いサイン」 |
| 3 | `slope9[t] >= rci_slope_min`(初期値 20) | 「RCI短期線の急角度」 |
| 4 | `RCI(14)[t] <= rci14_max`(初期値 −50)で、かつ上向きに転じている(6.4) | 「中期線が−70以下から短期線上がると底感」 |
| 5 | `close[t] > SMA(5)[t]` | 「ローソク足が短期線の上」 |
| 6 | 入り口の値段から上に `round_number_margin`(初期値 0.5%)以内に「キリのいい数字」がない | 「キリ番の壁」の逆用(壁の直下では買わない) |

**キリのいい数字の定義**: 値段の有効数字で上から2桁目までが 0 になる数。例: BTC が 67,xxx ドルなら 68,000。NVDA が 18x ドルなら 190。SOL が 1xx ドルなら 200 や 150(50 刻みも含める: 上から2桁目が 0 または 5)。実装役は銘柄の価格帯に関わらず動く汎用の式で書き、試験で BTC・SOL・NVDA の3例を確かめる。

### 7.5 注文の出し方(入り口)

- 条件を満たした足 t の**終値**を指値として、足 t+1 の開始時に買い指値を出す。
- 検証での約定の判定(保守的): 足 t+1 の**安値 ≤ 指値** なら、指値で約定したとみなす。等号でも約定。
- 足 t+1 で約定しなければ注文を取り消し、見送る。追いかけない。
- 同時に持てる玉は**全銘柄合わせて1つ**。持ち玉がある間は他の銘柄の入り口判定もしない(段階4で資金が増えたらボスの指示で見直す)。

### 7.6 出口(入る前に3つ決める)

| 出口 | 値段・条件 | 検証での約定の判定 | コスト |
|---|---|---|---|
| 損切り | 入値 − ATR(14)[t] × `stop_atr`(初期値 1.0) | 足の**安値 ≤ 損切り値段**なら、損切り値段 − 滑りで約定 | taker + slippage_stop |
| 利確 | 入値 + ATR(14)[t] × `take_atr`(初期値 2.0) | 足の**高値 ≥ 利確値段**なら、利確値段で約定 | maker |
| 時間切れ | 保有が `max_bars` 本に達したら、その足の終値で手仕舞い | 終値で約定 | taker |

- 同じ足で損切りと利確の両方に届いた場合は**損切りが先に起きたとみなす**(保守的)。
- `max_bars` の初期値: 1分足 15本、5分足 12本(60分)、15分足 8本(2時間)、1時間足 6本(6時間)。
- ATR は入った時点の値で固定する。保有中に動かさない。

**出口方式 B(追加の出口)**: 上の3つに加えて、「`slope9[t] < 0` になった足の終値で手仕舞い(taker)」を足す。元手法の「パラボ陰転前に RCI を見て利確」の数値化。
→ 検証では**方式 A(3つ)と方式 B(4つ)の両方**を流し、判定表に並べる。

### 7.7 安全装置(検証・紙上・本番すべてで同じ)

| 装置 | 内容 |
|---|---|
| 1日の損失上限 | その日(UTC)の確定損失が資金の `daily_loss_limit`(初期値 3%)に達したら、その日は新規に入らない |
| 連敗停止 | `max_consecutive_losses`(初期値 5)連敗したら、次の UTC 0時まで新規に入らない |
| 欠損明け | データ欠損の直後 10本は入らない(5.4) |
| 強制手仕舞い | 米国株は 15:55 NY時間。仮想通貨はなし |

### 7.8 パラメータ一覧

| 名前 | 初期値 | 探索範囲(前半データでのみ) | 意味 |
|---|---|---|---|
| rci_slope_min | 20 | 10, 15, 20, 25, 30 | RCI(9) の傾きの最低値 |
| rci14_max | −50 | −70, −60, −50, −40 | RCI(14) の上限 |
| macd_lookback | 3 | 1, 2, 3, 5 | GC を数える範囲 |
| stop_atr | 1.0 | 0.75, 1.0, 1.5 | 損切り幅(ATR 倍) |
| take_atr | 2.0 | 1.5, 2.0, 2.5, 3.0 | 利確幅(ATR 倍) |
| max_bars | 足ごと(7.6) | 固定 | 時間切れ |
| round_number_margin | 0.5% | 固定 | キリ番の除外幅 |
| daily_loss_limit | 3% | 固定 | 1日の損失上限 |
| max_consecutive_losses | 5 | 固定 | 連敗停止 |

- 探索範囲の全組み合わせは 5×4×4×3×4 = 960 通り。1設定(足×銘柄)あたり 960 回の検証を**前半データだけ**で流し、最も良い組み合わせを**1つだけ**選ぶ。選ぶ基準は「総利益÷総損失」(8.4)。
- 選んだ1組を後半データでそのまま流す。後半で数字をいじることは**禁止**。

## 8. 検証(段階2)

### 8.1 検証の単位

| 軸 | 値 |
|---|---|
| 足 | 1分、5分、15分、1時間 |
| 銘柄 | 第1段階: BTC・ETH・SOL / 第2段階: xyz:NVDA・xyz:TSLA・xyz:XYZ100 |
| 出口方式 | A、B |

第1段階は 4×3×2 = 24 の判定行。第2段階で 24 行追加。

### 8.2 期間と分割

- 使えるデータ全部を時間順に並べ、**最初の60%を前半、残り40%を後半**とする。
- 前半でパラメータを選び(7.8)、後半で確認する。
- 最低必要期間: 後半が 90日以上。足りない場合は判定を「データ待ち」とし、判定表にそう書く。足りるまで毎日データを貯めて再実行する。

### 8.3 資金と玉の大きさ(検証用)

- 検証用の資金: 1,000 ドル(計算を分かりやすくするための仮の数字。本番の資金ではない)。
- 1回の玉: 資金の 100%(レバレッジ1倍)。損益は率(%)で出すので資金額に意味はないが、Hyperliquid の最低注文額(10ドル)を下回らないよう 1,000 ドルにしてある。
- 複利はしない(毎回 1,000 ドルで入る)。

### 8.4 判定表の列(1行=1設定)

| 列 | 内容 |
|---|---|
| 足 / 銘柄 / 出口方式 | 設定の識別 |
| 選んだパラメータ | 前半で選んだ1組 |
| 期間(前半 / 後半) | 開始日〜終了日 |
| 取引回数(前半 / 後半) | 約定した回数 |
| 勝率(前半 / 後半) | 利益が出た取引の割合 |
| 総利益÷総損失(前半 / 後半) | 1.0 より大きければ儲かっている。以下「PF」と書く |
| 平均純利益 / 1取引(ドル) | 手数料・滑り・資金調達料を引いた後 |
| 最大の落ち込み(後半) | 資金の高値からの最大下落率(%) |
| 月別利益の最大比率(後半) | 最も儲かった1か月の利益 ÷ 後半の総利益。偏りの指標 |
| 時間帯別成績(仮想通貨のみ) | UTC 0〜23 時台ごとの PF(別表) |
| 除外日数 | 欠損で除外した日数 |
| 判定 | 合格 / 不合格 / 判定不能 / データ待ち |
| 否決理由 | 不合格の場合、どの基準に引っかかったか |

### 8.5 合格基準(先に固定。後から緩めない)

**後半データ**で次をすべて満たすこと。

| # | 基準 | 数字 |
|---|---|---|
| 1 | 取引回数 | 300回以上(届かない場合は「判定不能」) |
| 2 | PF | 1.30 以上 |
| 3 | 前半との差 | 前半の PF − 後半の PF が 0.5 以内(前半で良すぎて後半で崩れるのは偶然を疑う) |
| 4 | 最大の落ち込み | 10% 以内 |
| 5 | 月別利益の偏り | 最大の1か月が総利益の 40% 以下 |
| 6 | 平均純利益 / 1取引 | 1,000ドルの玉で 1.0 ドル以上(ボスの方針「1取引の最低純利益は1ドル以上」) |
| 7 | 隣の足 | 同じ銘柄・同じ出口方式で、隣の足(1分なら5分、15分なら5分と1時間)の後半 PF が 0.9 以上(大負けしていない) |

- 基準7は「その足だけ飛び抜けて良い」を偶然と疑うためのもの。隣の足が「判定不能」の時は基準7を適用しない。
- 7つ全部満たす→**合格**。1つでも満たさず、かつ基準1は満たす→**不合格**。基準1を満たさない→**判定不能**。

### 8.6 否決メモ

不合格・判定不能の設定ごとに1ファイル(`memos/reject_<足>_<銘柄>_<出口>.md`)。内容:

1. 設定と選んだパラメータ
2. 引っかかった基準と、その数字
3. 負けの内訳: 損切り回数・利確回数・時間切れ回数と、それぞれの合計損益
4. コスト内訳: 手数料合計・滑り合計・資金調達料合計。**「コストを0にしたら PF はいくつか」**も書く(コスト負けか、ロジック負けかを切り分けるため)
5. 入り口条件6つのうち、どれが最も取引を減らしているか(各条件を1つ外した時の取引回数)
6. 実装役の所見(1〜3行。推測は「推測」と明記)

### 8.7 検証の実行

```
python -m kaikai_bot.backtest --stage 1          # 第1段階 24行
python -m kaikai_bot.backtest --stage 2          # 第2段階 24行(段階5で有効化)
python -m kaikai_bot.backtest --coin BTC --tf 15m --exit A   # 1設定だけ
```

- 出力: `reports/judgement_<日付>.md`(判定表)と `reports/judgement_<日付>.csv`、否決メモ。
- 同じデータ・同じ設定で2回流したら、小数点以下6桁まで同じ結果になること(再現性。段階2の試験に含める)。
- 24行の完走時間が 1 台の普通のパソコンで 2 時間以内に収まるよう作る(960通りの探索があるため、1分足は計算の無駄を省く。例: 指標は1回だけ計算して使い回す)。

## 9. 紙上運転(段階3)

### 9.1 対象

- 検証で**合格**した設定すべて(なければ、不合格の中で後半 PF が最も高い設定を**1つ**、「暫定設定」として動かす。これは運転の仕組みを動かして確かめるためで、昇格の対象にはしない)。

### 9.2 動き方

- 1分足を API から取り続け(5.5 の収集と同じ入口)、設定の足が確定するたびに第7章の判断を行う。
- 注文は**出さない**。「出したつもり」の注文を記録し、約定の判定は検証と同じ規則(7.5、7.6)を本番の足に当てて行う。
- コストも検証と同じ数字で引く。
- 記録は `data/paper.db` に。取引ごとに: 設定・入った時刻と値段・出た時刻と値段と理由・コスト・純損益。

### 9.3 合格基準(昇格候補になる条件)

| # | 基準 | 数字 |
|---|---|---|
| 1 | 期間 | 連続 28 日以上 |
| 2 | 取引回数 | 50回以上 |
| 3 | PF | 1.20 以上 |
| 4 | 検証との差 | 紙上の PF が、検証の後半 PF の 70% 以上(検証で 1.5 なら紙上で 1.05 以上)。大きく下回る時は検証の作りを疑い、報告する |
| 5 | 最大の落ち込み | 10% 以内 |

満たした設定は「昇格候補」として監視画面に表示する。**昇格の判断はボスが行う**。

### 9.4 止まらない作り

- API 失敗は 3 回まで再試行、それ以上は警告を出して次の足で再開。
- プログラムが落ちたら自動で再起動(OS のサービス機能か、監視用の小さなスクリプト)。再起動後は `paper.db` から持ち玉の状態を読み戻す。
- 24時間動くので、ボスのパソコンで動かすか、安い常時稼働のサーバーで動かすかはボスが決める(第17章)。

## 10. 少額本番(段階4)

### 10.1 開始の条件(すべて満たす)

1. 紙上運転の昇格候補が 1 つ以上ある
2. ボスが「この設定で開始」と明示する
3. ボスが Hyperliquid の口座と API 用の鍵(署名用の秘密鍵)を用意し、資金を入れている
4. 資金額をボスが決めている(Commander の案: **100 ドル・1設定・レバレッジ1倍**。段階4の目的は儲けではなく「注文→約定→手仕舞い」が本物のお金で正しく動くことの確認)

### 10.2 注文の実装

- Hyperliquid の取引用 API(署名が必要)を使う。公式の Python SDK があればそれを使い、無ければ公式文書どおりに署名を実装する。
- 入り口: 指値(post-only。板に置くだけで、すぐ約定する場合は注文自体が取り消される種類の注文。maker 手数料になる)。次の足で約定しなければ取り消す。
- 利確: 指値(post-only)。入った直後に置く。
- 損切り: 逆指値(Hyperliquid の trigger 注文)。入った直後に置く。発動したら成行。
- 時間切れ・出口方式Bの手仕舞い: 成行。
- 入った直後に利確と損切りの両方を置く(入値が確定してから、ATR で計算した値段で)。**どちらかが約定したら、もう一方を必ず取り消す**。取り消し失敗は最優先の警告。

### 10.3 鍵の管理

- 秘密鍵は環境変数か、リポジトリの外のファイル(`~/.kaikai-bot/secret`)に置く。**リポジトリに入れない**。`.gitignore` に書く。
- 鍵の権限は取引のみ。出金権限は持たせない(Hyperliquid の API ウォレットは出金できない作りだが、念のため確認する)。

### 10.4 本番の安全装置(7.7 に加えて)

| 装置 | 内容 |
|---|---|
| 持ち玉の照合 | 10 秒ごとに API で実際の持ち玉を取り、自分の記録と違ったら新規停止+警告 |
| 注文の照合 | 利確・損切りの注文が板に残っているか 10 秒ごとに確認。消えていたら置き直し、置き直せなければ成行で手仕舞い |
| 緊急停止 | ファイル `STOP` をリポジトリ直下に置いたら、持ち玉を成行で全部手仕舞いし、新規を止める。画面にもボタンを付ける |
| 資金の下限 | 口座残高が開始時の 80% を下回ったら、全部手仕舞いして停止。再開はボスの指示 |

### 10.5 段階4の完了条件

- 28 日間、停止事故(照合の不一致・取り消し失敗)なしで動く
- 取引が 20 回以上ある
- 純損益がプラスかマイナスかに関わらず、**紙上運転の損益との差が説明できる**(滑り・約定しなかった注文の数で)。説明できない差があれば報告し、ボスが続行か停止かを決める

## 13. 試験

### 13.1 単体試験(必須)

| 対象 | 内容 |
|---|---|
| 指標(6.6) | 既知の値との照合、計算不能期間の扱い |
| 上位足の生成(5.3) | 1分足 60 本から 5分・15分・1時間足を作り、始値・高値・安値・終値・出来高が正しい。欠損があると作られない |
| キリのいい数字(7.4) | BTC・SOL・NVDA の価格帯で正しい数が出る |
| 時間帯フィルタ(7.2) | 夏時間・冬時間の両方で NY 9:50〜15:30 が正しく UTC に変換される。祝日に入らない |
| 約定判定(7.5、7.6) | 指値に届く/届かない、損切りと利確が同じ足で両方届く(損切り優先)、時間切れ |
| 安全装置(7.7) | 1日の損失上限、連敗停止、欠損明け |
| 検証の再現性(8.7) | 同じ入力で2回流して同じ結果 |

### 13.2 結合試験

- 小さな人工データ(100 本程度の1分足)で、取引が「入る→利確」「入る→損切り」「入る→時間切れ」の3通りそれぞれ1回ずつ起きることを確かめる。損益・コストの数字を手計算と照合する。

### 13.3 試験の運用

- 本体(`kaikai_bot/` の実行コード)を変えた時だけ全試験を流す。文書・設定・試験だけの変更では関係する試験だけでよい。
- 段階の完了報告には、試験の通過数(例: 48/48)を書く。

## 15. 禁止事項

1. 合格基準(8.5、9.3)を後から緩めること。変えるなら文書の版を上げ、ボスの承認を得る。

## 16. 報告の形式

各段階の終わりに、次の順で書く。専門用語・関数名・ログの識別子は出さず、日本語で書く。

1. **結論**(1文): 段階 N は完了したか、していないか
2. 完了条件の充足(段階ごとの表に ○×)
3. 数字: 試験の通過数、データの日数、判定表の要約(合格/不合格/判定不能/データ待ちの数)
4. 自分で決めたこと(DESIGN_NOTES に書いた項目の見出しだけ)
5. 未解決・気になる点
6. 次に進む段階
