## 1. 目的と「勝ち」の定義

### 1.1 目的

X(旧Twitter)の投資家 kaikai 氏が公開した日本株1分足のスキャルピング手法(以下「元手法」)を、人の勘に頼らない機械のルールに書き直し、Hyperliquid の暗号資産と米国株の永久先物で**本当に利益が出るかを数字で判定し**、出るならそのルールで自動売買する。

### 1.2 「勝ち」の定義(優先順)

1. **第1の勝ち**: 正式判定(8.2)で合格する設定(足×銘柄×出口方式×パラメータ)が1つ以上見つかり、紙上運転(注文を出さずに本番の値動きで動かすこと)でも合格し、少額本番で**手数料と資金調達料を引いた後の純利益がプラス**で4週間終わること。
2. **第2の勝ち**: 全設定が不合格になり、「なぜ負けるか」が否決メモとして数字で残ること。これも勝ちです。勘でやって負けるより価値があります。
3. **負け**: 判定ができない状態(データ不足・バグ・基準の後出し変更)で終わること。これだけが負けです。

### 1.3 やらないこと

- 元手法のうち機械化できない部分(板読み、キリのいい数字の攻防戦、ローソク足の形、ゴールデンクロスの「綺麗さ」)は**最初から捨てる**。後から足さない。
- ショート(売りから入る取引)は第2版でもやらない。ロング(買いから入る取引)のみ。
- 数秒で手仕舞うスキャルピングはやらない。保有は数分〜数時間。
- bot-factory との連携(自動・手動とも)は作らない。

## 3. 全体像

### 3.1 工程(左から右へ流れる)

```
データ収集 → 指標計算 → 検証(中間報告→予備判定→正式判定) → 判定表・否決メモ → 紙上運転 → 少額本番 → 監視
```

### 3.2 段階(作る順番)

| 段階 | 作るもの | 完了の条件 | 状態(2026-10-26) |
|---|---|---|---|
| 1 | データ収集・保存・上位足の生成・指標計算 | 6銘柄の1分足が毎時自動で貯まり、指標の単体試験が全部通る | 完了 |
| 2 | 検証エンジン・判定表・否決メモ | 24設定(足4×銘柄3×出口2)の判定表が1コマンドで出る | 完了(第2版のルールへの差し替えが必要) |
| 3 | 紙上運転(24設定)・監視画面 | 24設定が24時間動き続け、画面で見える | 着手中 |
| 4 | 少額本番 | ボスの指示で開始。鍵と資金の用意を待つ(ここだけ停止点) | 未着手 |
| 5 | 米国株(HIP-3)の判定表への追加 | 判定表に米国株3銘柄×足4×出口2の24行が加わる | 収集だけ開始済み |

段階5は段階3と並行で進めてよい(データが貯まり次第)。

### 3.3 実装役の進め方

- 段階1→2→3→5は、ボスや Commander の合図を待たず、完了条件を満たしたら自分で次に進む。各段階の終わりに報告だけ出す。
- 段階4だけは、ボスが鍵と資金を用意するまで着手しない。
- 試験の軽い不備(引数の渡し忘れ、試験用データの不足など、期待値・製品コード・既存試験を変えずに直せるもの)は、止まらずに自力で直して進む。
- この文書に書いていないことで判断に迷ったら、「シンプルで確実」な方を選び、docs/DESIGN_NOTES.md に「決めたことと理由」を書き、報告に見出しだけ載せる。推測・しきい値・設定項目を勝手に増やさない。
- 第1版で実装役が DESIGN_NOTES に記録した決め事は、第2版でも有効とする(第2版の本文と食い違うものを除く)。主なものは本文に取り込んだ。

## 5. データ

### 5.1 取得元

- Hyperliquid の公開 API(情報取得用の入口 `https://api.hyperliquid.xyz/info`)。鍵は不要。
- 要求の種類は `candleSnapshot`(足の取得)。銘柄・足の種類(`1m`)・開始時刻・終了時刻を指定する。
- **取れるのは直近約5,190本(1分足で約3.6日分)だけ**(2026-10-25 実測、6銘柄とも)。そのため毎時の収集で貯めたものが長期の検証データの唯一の出どころになる。
- 公式の過去記録の保管庫(AWS)は今は使わない(ボス決定 2026-10-25)。

### 5.2 保存形式

**貯める場所(GitHub の data 枝)**
- `candles/<銘柄>/<UTC日付>.csv`。銘柄名の「:」は「_」に置き換える(xyz:NVDA → xyz_NVDA)。
- 列: ts_open, open, high, low, close, volume, trades(5.2 の表と同じ意味)。
- 欠損の記録 `gaps.log` と収集の状態 `collect_status.json` も data 枝に置く。
- 確定した足だけ保存する(作りかけの足は保存しない)。

**使う場所(パソコンの SQLite)**
- `data/market.db`、表 `candles_1m`

| 列 | 型 | 意味 |
|---|---|---|
| coin | 文字 | 銘柄コード(例 `BTC`、`xyz:NVDA`) |
| ts_open | 整数 | 足の開始時刻(UTC、ミリ秒) |
| open | 実数 | 始値 |
| high | 実数 | 高値 |
| low | 実数 | 安値 |
| close | 実数 | 終値 |
| volume | 実数 | 出来高 |
| trades | 整数 | 約定回数 |
| fetched_at | 整数 | 取得した時刻(UTC、ミリ秒) |

- 主キー: (coin, ts_open)。同じ足を二度取ったら上書き。
- 1分足だけを保存する。5分・15分・1時間・4時間足は保存せず、必要な時に1分足から計算で作る(5.3)。

### 5.3 上位足の生成規則

| 足 | 作り方 |
|---|---|
| 5分足 | UTC で 分が 0,5,10,…,55 から始まる5本の1分足をまとめる |
| 15分足 | UTC で 分が 0,15,30,45 から始まる15本をまとめる |
| 1時間足 | UTC で 分が 0 から始まる60本をまとめる |
| 4時間足 | UTC で 0,4,8,12,16,20 時から始まる240本をまとめる(1時間足の「1つ上の足」用) |

- まとめ方: 始値=最初の1分足の始値、高値=最大、安値=最小、終値=最後の終値、出来高=合計。
- 1分足が1本でも欠けている区間の上位足は**作らない**(欠損扱い)。穴埋めや補間はしない。

### 5.4 欠損の扱い

- 欠損区間は `gaps.log` に銘柄・開始・終了を記録する。
- 検証では欠損区間をまたぐ取引は発生させない(欠損の直前で持ち玉を終値で強制手仕舞いし、欠損明け10本は新規に入らない)。
- 指標は欠損をまたいで(残った足を順につないで)計算してよい。取引が欠損をまたがないので実害がない。
- 除外日: UTC の1日(1,440本)のうち95%に届かない日は検証から除外する。データの最初の日・最後の日も同じ基準。判定表の備考に除外日数を書く。

### 5.5 収集の運転(第2版で差し替え)

- `python -m kaikai_bot.collect --store <保管庫>` を **GitHub の自動実行(`.github/workflows/collect.yml`)で1時間に1回**動かし、data 枝に日ごとのファイルで貯める。
- パソコンでは `python -m kaikai_bot.collect --from-github` で data 枝を取り込み、`data/market.db` を作る。
- 毎回「保存庫の最新時刻の1時間前」から現在までを取り直す(重複は上書き)。保存庫が空なら取れる最も古い足から。
- 失敗したら次回に自動で取り直す。3回連続失敗で `logs/alerts.log` に警告を書き、監視画面に出す。

### 5.6 コストの設定値(設定ファイル `config/costs.yaml`)

| 項目 | 初期値 | 意味 |
|---|---|---|
| taker_fee | 0.045% | 板を取りに行く注文の手数料 |
| maker_fee | 0.015% | 板に置いて待つ注文の手数料 |
| hip3_fee_multiplier | 2.0 | HIP-3 銘柄は手数料をこの倍にする |
| slippage_stop | 0.02% | 損切り(逆指値→成行)にかかる滑り |
| slippage_entry | 0.00% | 入り口は指値なので滑りなし |
| funding_per_hour | 0.001% | 保有1時間あたりの資金調達料(平均の見積もり)。保有時間に比例して引く |

- 検証では**入り口 maker、利確 maker、損切り taker+滑り、時間切れ・方式Bの手仕舞い・強制手仕舞い taker**として計算する。
- 資金調達料の保有時間は「約定した足の始まりから手仕舞った足の終わりまで」。
- これらは「保守的(損益を悪く見積もる)」に設定する。実装役が公式文書で確認した日付を設定ファイルに書く。

## 6. 指標の定義(計算式)

すべて終値ベース。`t` は現在の足、`t-1` は1本前。計算に必要な本数が足りない期間は「計算不能」とし、その足では売買判断をしない。細かい計算の決まり(指数移動平均の初期値など)は、試験の照合相手である TA-Lib に合わせる(第1版で実装済み)。

### 6.1 単純移動平均線 SMA(n)

直近 n 本の終値の平均。n = 5, 25, 75 の3本。

**上向きの定義**: `SMA(n)[t] > SMA(n)[t-10]`(10本前より高い)。

### 6.2 パラボリック SAR

標準の計算(Wilder 方式)。加速因子の初期値 0.02、増分 0.02、上限 0.20。
- **陽**: SAR の値が足の安値より下にある。**陰**: SAR の値が足の高値より上にある。
- **第2版では入り口の条件に使わない**。入った時点の陽/陰を取引記録に残し、判定表に「陽で入った取引の割合と、その PF」を出す(第3版でパラボリックを戻すかどうかの材料)。

### 6.3 MACD(12, 26, 9)

- MACD線 = EMA(12) − EMA(26)、シグナル線 = MACD線の EMA(9)
- **ゴールデンクロス**: `MACD[t-1] <= シグナル[t-1]` かつ `MACD[t] > シグナル[t]`
- **マイナス圏でのゴールデンクロス**: ゴールデンクロスが起き、かつ `MACD[t] < 0`

### 6.4 RCI(n)(順位相関指数)

直近 n 本について、時間の順位(新しいほど大きい)と終値の順位(高いほど大きい)の差 d を各足で求め、

```
RCI(n) = (1 − 6 × Σ(d²) / (n × (n² − 1))) × 100
```

範囲は −100〜+100。n = 9(短期)と 14(中期)。同じ終値が複数ある時の順位は平均順位。

- **傾き**: `slope9[t] = RCI(9)[t] − RCI(9)[t-1]`
- **急角度**: `slope9[t] >= rci_slope_min`
- **中期の底の印**: `RCI(14)[t-1] <= rci14_max` かつ `RCI(14)[t] > RCI(14)[t-1]` かつ `RCI(14)[t-1] <= RCI(14)[t-2]`(深い所から上向きに転じた)

### 6.5 ATR(14)

真の値幅 TR = max(高値−安値, |高値−前終値|, |安値−前終値|)。ATR はその Wilder 平均(14本)。損切り・利確の幅に使う。

### 6.6 キリのいい数字(第2版で定義を統一)

- **刻み幅** `step` = 値段の桁数から決める。`step = 10^(floor(log10(値段)) − 1)`。
  例: BTC 67,420 → 1,000。ETH 2,480 → 100。SOL 179 → 10。NVDA 185 → 10。XYZ100 24,800 → 1,000。
- **キリのいい数字** = step の倍数(上から2桁で丸めた数)。
- **壁の直下**: 値段 p のすぐ上にある step の倍数を R とした時(p ちょうどが倍数なら R = p)、`R − p <= step × 0.1` なら「壁の直下」。
  例: BTC 67,950 → R=68,000、差 50 ≤ 100 → 直下。BTC 67,420 → 差 580 > 100 → 直下でない。SOL 179.2 → R=180、差 0.8 ≤ 1 → 直下。NVDA 185.3 → R=190、差 4.7 > 1 → 直下でない。

### 6.7 指標の単体試験

- 各指標について既知の値(TA-Lib で作った表)と小数点以下4桁で一致すること。RCI は同値の順位処理も含む。
- キリのいい数字は上の6例すべてを試験に入れる。

## 7. 戦略ロジック v2(ロングのみ)

### 7.1 全体の考え方

「上の流れの中で、押し目(いったん下がった所)から反発し始めた瞬間に買う」。流れは**長い物差し**(75本線と1つ上の足)で測り、押し目と反発は**短い物差し**(RCI・MACD・5本線)で測る。第1版は両方を同じ物差しで測って打ち消し合っていた。判断は毎足の**確定時**に1回だけ行う。足の途中では何もしない。

### 7.2 時間帯フィルタ

| 対象 | 入ってよい時間 |
|---|---|
| 仮想通貨 | 24時間(フィルタなし)。判定表には「入った時刻(UTC の時間帯 0〜23)」別の成績を別表で出す |
| 米国株(HIP-3) | 指値を出す時刻(足 t の確定時刻)がニューヨーク時間 9:50 以上 15:30 未満で、土日・休日でない時だけ。約定を見る次の足の終わりが 15:55 を過ぎるなら入らない。持ち玉は「次の足の終わりが 15:55 を過ぎる足」の終値で強制手仕舞い |

- 夏時間・冬時間は `America/New_York` の時刻計算ライブラリに任せる。
- 休日表は `config/us_holidays.yaml`(NYSE 公式から転記、2026・2027年。過去データを補う時はその年を足す)。13時までの短縮取引日は第2版でも扱わない(記録だけ)。

### 7.3 環境フィルタ(流れが上かどうか)

次の2つを**両方**満たす時だけ、入り口の判定に進む。

| # | 条件 | 式 |
|---|---|---|
| 環1 | 同じ足で、終値が長期線の上 | `close[t] > SMA(75)[t]` |
| 環2 | 1つ上の足で、25本線が上向き | 上の足の `SMA(25)[u] > SMA(25)[u-10]` |

- 上の足の対応: 1分→5分、5分→15分、15分→1時間、1時間→4時間。
- 「上の足 u」は、足 t の確定時刻までに**閉じている最新の上の足**。それが直前の区間の足でない(欠けている)時は環2を満たさない扱い(先の値を覗かないため)。

### 7.4 入り口の条件

足 t が確定した時点で、**必須3つすべて**と、**押し目の印のどちらか1つ以上**を満たすこと。

**必須(3つとも)**

| # | 条件 | 式 | 元手法との対応 |
|---|---|---|---|
| 必1 | RCI短期が急角度で上向き | `slope9[t] >= rci_slope_min` | 「RCI短期線の急角度で in」(元手法の核心) |
| 必2 | 終値が短期線の上 | `close[t] > SMA(5)[t]` | 「ローソク足が短期線の上」 |
| 必3 | キリのいい数字の壁の直下でない | 6.6 で「直下」に当たらない | 「キリ番の壁」の逆用 |

**押し目の印(どちらか1つ以上)**

| # | 条件 | 式 | 元手法との対応 |
|---|---|---|---|
| 印A | MACDがマイナス圏でゴールデンクロスしたばかり | 直近 `macd_lookback` 本以内(t を含む)に 6.3 のマイナス圏GC | 「マイナス圏のGCはかなりの買いサイン」 |
| 印B | RCI中期が深い所から上向きに転じた | 6.4 の「中期の底の印」 | 「中期線が −70 以下から短期線上がると底感」 |

**記録だけ(条件にしない)**: 入った時のパラボリックの陽/陰、印A・印Bのどちらで入ったか(両方なら「両方」)。

### 7.5 注文の出し方(入り口)

- 条件を満たした足 t の**終値**を指値として、足 t+1 の開始時に買い指値を出す。
- 検証での約定の判定(保守的): 足 t+1 の**安値 ≤ 指値**なら、指値で約定したとみなす。
- 足 t+1 で約定しなければ取り消し、見送る。追いかけない。
- **持ち玉の数**
  - 検証・紙上運転: **設定ごとに独立に1つ**。設定同士は互いに影響しない(比べるため)。
  - 少額本番: **全体で1つ**(資金が1設定分のため)。
- 手仕舞った足が閉じた瞬間から、次の判断ができる。

### 7.6 出口(入る前に3つ決める)

| 出口 | 値段・条件 | 検証での約定の判定 | コスト |
|---|---|---|---|
| 損切り | 入値 − ATR(14)[t] × `stop_atr` | 足の**安値 ≤ 損切り値段**なら、損切り値段 − 滑りで約定 | taker + slippage_stop |
| 利確 | 入値 + ATR(14)[t] × `take_atr` | 足の**高値 ≥ 利確値段**なら、利確値段で約定 | maker |
| 時間切れ | 保有が `max_bars` 本に達したら、その足の終値で手仕舞い | 終値で約定 | taker |

- ATR は入った時点(足 t)の値で固定する。
- 約定した足を保有1本目と数える。**約定した足では利確を見ない**(高値が約定の前か後か分からないため。損切りだけ見る)。
- 同じ足で複数の出口に当たった時の順番: 損切り → 利確 → 方式B → 時間切れ → 強制手仕舞い(欠損の直前・米国株の引け前)。
- `max_bars` の初期値: 1分足 15本、5分足 12本、15分足 8本、1時間足 6本。

**出口方式 B(追加の出口)**: 上の3つに加えて「`slope9[t] < 0` になった足の終値で手仕舞い(taker)」。元手法の「パラボ陰転前に RCI を見て利確」の数値化。
→ 検証・紙上運転とも**方式 A(3つ)と方式 B(4つ)の両方**を流す。

### 7.7 安全装置(検証・紙上・本番すべてで同じ。設定ごとに独立に数える)

| 装置 | 内容 |
|---|---|
| 1日の損失上限 | その日(UTC、足の確定時刻で決める)に手仕舞った取引の純損益の合計が資金の −`daily_loss_limit` 以下になったら、その日は新規に入らない |
| 連敗停止 | 純損益がマイナスの取引が `max_consecutive_losses` 回続いたら、その日の UTC 24時まで新規に入らない。明けたら数え直す |
| 欠損明け | データ欠損の直後 10本は入らない |
| 強制手仕舞い | 米国株は 7.2 のとおり。仮想通貨はなし |

### 7.8 パラメータ一覧(第2版で縮小)

| 名前 | 初期値 | 探索範囲(前半データでのみ) | 意味 |
|---|---|---|---|
| rci_slope_min | 20 | 10, 20, 30 | RCI(9) の傾きの最低値 |
| rci14_max | −50 | −60, −50, −40 | 印B の「深い所」の上限 |
| macd_lookback | 3 | 2, 3, 5 | 印A の GC を数える範囲 |
| stop_atr | 1.0 | 0.75, 1.0, 1.5 | 損切り幅(ATR 倍) |
| take_atr | 2.0 | 1.5, 2.0, 3.0 | 利確幅(ATR 倍) |
| max_bars | 足ごと(7.6) | 固定 | 時間切れ |
| daily_loss_limit | 3% | 固定 | 1日の損失上限 |
| max_consecutive_losses | 5 | 固定 | 連敗停止 |

- 組み合わせは 3×3×3×3×3 = **243 通り**。
- **選び方**(正式判定の前半データでのみ):
  1. 前半の取引回数が、その足の最低回数(8.5 の表)に**届く組だけ**を候補にする。
  2. 候補の中で PF が最も高い組を選ぶ。同じなら取引回数が多い組、それも同じなら探索表の先の組。
  3. 候補が1つもなければ**探索せず初期値を使う**(判定表にそう書く)。
- 選んだ1組を後半データでそのまま流す。後半で数字をいじることは**禁止**。

## 8. 検証(段階2)

### 8.1 検証の単位

| 軸 | 値 |
|---|---|
| 足 | 1分、5分、15分、1時間 |
| 銘柄 | 第1段階: BTC・ETH・SOL / 第2段階: xyz:NVDA・xyz:TSLA・xyz:XYZ100 |
| 出口方式 | A、B |

第1段階は 24 行、第2段階で 24 行追加。

### 8.2 三段構えの判定(第2版)

| 時点(丸1日そろった日数) | 名前 | やること | 使い道 |
|---|---|---|---|
| 30日 | **中間報告** | 24設定それぞれの「1日あたりの合図回数」「約定回数」と、各条件を1つ外した時の合図回数を表にする。判定はしない | 最低回数に届く見込みがない設定を早く知る。ボスが第3版を検討する材料 |
| 90日 | **予備判定** | パラメータ探索なし(初期値固定)で、全データに 8.5 の基準を当てる。結果は「予備合格/予備不合格/判定不能」 | 早い段階の読み。昇格には使わない |
| 225日(後半90日が確保できた時) | **正式判定** | 最初の60%を前半、残り40%を後半とし、前半でパラメータを選び(7.8)、後半で 8.5 を当てる | **昇格の根拠はこれだけ** |

- 中間報告・予備判定の結果を見てパラメータや基準を変えることは禁止(15章)。変えるなら第3版として理由を記録する。
- 正式判定は 225日以降、データが増えるたびに再実行してよい(前半・後半の境目はその時点の 60% の位置)。
- 前半・後半の分け方: 指値を出す時刻で分ける。前半の終わりに持っていた玉は手仕舞いまで追う。後半は安全装置の状態を空にして始める。データの終わりで持ち玉が残った取引は数えない。

### 8.3 資金と玉の大きさ(検証用)

- 検証用の資金: 1,000 ドル(計算用の仮の数字)。1回の玉は資金の 100%(レバレッジ1倍)。複利はしない。

### 8.4 判定表の列(1行=1設定)

| 列 | 内容 |
|---|---|
| 足 / 銘柄 / 出口方式 | 設定の識別 |
| 選んだパラメータ | 正式判定で選んだ1組(候補なしなら「初期値」) |
| 期間(前半 / 後半) | 開始日〜終了日 |
| 取引回数(前半 / 後半) | 約定した回数 |
| 勝率(前半 / 後半) | 利益が出た取引の割合 |
| PF(前半 / 後半) | 総利益÷総損失 |
| 平均純利益 / 1取引(ドル) | コストを引いた後 |
| 最大の落ち込み(後半) | 資金の高値からの最大下落率(%) |
| 月別利益の最大比率(後半) | 最も儲かった1か月の利益 ÷ 後半の総利益 |
| 印A / 印B / 両方 の内訳 | それぞれで入った取引の回数と PF |
| パラボ陽の内訳 | 陽で入った取引の割合と、陽・陰それぞれの PF |
| 時間帯別成績(仮想通貨のみ) | UTC 0〜23 時台ごとの PF(別表) |
| 除外日数 | 欠損で除外した日数 |
| 判定 | 合格 / 不合格 / 判定不能 / データ待ち(予備判定は「予備」を頭に付ける) |
| 否決理由 | 不合格の場合、どの基準に引っかかったか |

### 8.5 合格基準(第2版。先に固定し、後から緩めない)

**後半データ**(予備判定では全データ)で次をすべて満たすこと。基準1・2は足ごとに違う。

| 足 | 基準1: 取引回数 | 基準2: PF |
|---|---|---|
| 1分 | 300 回以上 | 1.30 以上 |
| 5分 | 200 回以上 | 1.35 以上 |
| 15分 | 120 回以上 | 1.40 以上 |
| 1時間 | 60 回以上 | 1.50 以上 |

(回数が少ない足ほど偶然で良く見えやすいので、その分だけ高い成績を要求する。)

| # | 基準(足に関係なく共通) | 数字 |
|---|---|---|
| 3 | 前半との差(正式判定のみ) | 前半の PF − 後半の PF が 0.5 以内 |
| 4 | 最大の落ち込み | 10% 以内 |
| 5 | 月別利益の偏り | 最大の1か月が総利益の 40% 以下(総利益が0以下なら満たさない) |
| 6 | 平均純利益 / 1取引 | 1,000ドルの玉で 1.0 ドル以上 |
| 7 | 隣の足 | 同じ銘柄・同じ出口方式で、隣の足(1分なら5分、5分なら1分と15分、15分なら5分と1時間、1時間なら15分)の PF が 0.9 以上。隣が「判定不能」「データ待ち」なら適用しない |

- 全部満たす→**合格**。基準1は満たすが他が1つでも満たさない→**不合格**。基準1を満たさない→**判定不能**。
- 後半が90日未満→**データ待ち**(正式判定のみ)。

### 8.6 否決メモ

不合格・判定不能の設定ごとに1ファイル(`memos/reject_<足>_<銘柄>_<出口>.md`)。内容:

1. 設定と選んだパラメータ
2. 引っかかった基準と、その数字
3. 負けの内訳: 損切り・利確・時間切れ・方式B・強制の回数と、それぞれの合計損益
4. コスト内訳: 手数料・滑り・資金調達料の合計と、**「コストを0にしたら PF はいくつか」**
5. 入り口の各条件(環1・環2・必1〜3・印A・印B)を1つ外した時の合図回数
6. 所見: 「取引回数不足」「コスト負け(コスト前は PF 1.0以上)」「ロジック負け(コスト前から PF 1.0未満)」「その他の基準」から選ぶ。推測は書かない

### 8.7 検証の実行

```
python -m kaikai_bot.backtest --stage 1 --mode frequency      # 中間報告(30日)
python -m kaikai_bot.backtest --stage 1 --mode preliminary    # 予備判定(90日)

## 9. 紙上運転(段階3・第2版で前倒し)

### 9.1 対象

- **第1段階の24設定すべて**を、**初期値のパラメータ**で今から動かす。段階5の準備ができたら第2段階の24設定も足す。
- 正式判定で合格が出たら、その設定は「選んだパラメータ」の版も追加で動かす(初期値の版は止めない)。

### 9.2 動き方

- 1分足を API から取り続け、設定の足が確定するたびに第7章の判断を行う。
- 注文は**出さない**。「出したつもり」の注文を記録し、約定の判定は検証と同じ規則(7.5、7.6)を本番の足に当てる。コストも検証と同じ数字で引く。
- 持ち玉は**設定ごとに独立に1つ**(7.5)。
- 記録は `data/paper.db`。取引ごとに: 設定・パラメータ版・入った時刻と値段・印A/B・パラボ陽/陰・出た時刻と値段と理由・コスト・純損益。
- **紙上運転の結果を見てパラメータや条件を変えない**(覗き見防止。15章)。

### 9.3 昇格候補になる条件

| # | 基準 | 数字 |
|---|---|---|
| 1 | 紙上の期間 | 連続 28 日以上 |
| 2 | 紙上の取引回数 | 50 回以上 |
| 3 | 紙上の PF | 1.20 以上 |
| 4 | 検証との差 | 紙上の PF が、正式判定の後半 PF の 70% 以上。**正式判定がまだ無い間はこの基準を外す** |
| 5 | 紙上の最大の落ち込み | 10% 以内 |
| 6 | **正式判定の合格** | その設定が正式判定で合格していること。24設定を同時に動かすと偶然1つは受かりやすいので、紙上だけでは昇格しない |

満たした設定は「昇格候補」として監視画面に表示する。**昇格の判断はボスが行う**。

### 9.4 止まらない作り

- API 失敗は 3 回まで再試行、それ以上は警告を出して次の足で再開。
- プログラムが落ちたら自動で再起動。再起動後は `paper.db` から持ち玉の状態を読み戻す。
- 動かす場所はボスが決める(第17章)。

## 10. 少額本番(段階4)

### 10.1 開始の条件(すべて満たす)

1. 9.3 の昇格候補が 1 つ以上ある(正式判定の合格を含む)
2. ボスが「この設定で開始」と明示する
3. ボスが Hyperliquid の口座と API 用の鍵を用意し、資金を入れている
4. 資金額をボスが決めている(Commander の案: 100 ドル・1設定・レバレッジ1倍)

### 10.2 注文の実装

- Hyperliquid の取引用 API(署名が必要)。公式の Python SDK があればそれを使う。
- 入り口: 指値(post-only)。次の足で約定しなければ取り消す。
- 利確: 指値(post-only)。入った直後に置く。
- 損切り: 逆指値(trigger 注文)。入った直後に置く。発動したら成行。
- 時間切れ・方式Bの手仕舞い: 成行。
- どちらかが約定したら、もう一方を必ず取り消す。取り消し失敗は最優先の警告。
- 持ち玉は**全体で1つ**。

### 10.3 鍵の管理

- 秘密鍵は環境変数か、リポジトリの外のファイル(`~/.kaikai-bot/secret`)。**リポジトリに入れない**。`.gitignore` に書く。
- 鍵の権限は取引のみ。出金権限を持たせない。

### 10.4 本番の安全装置(7.7 に加えて)

| 装置 | 内容 |
|---|---|
| 持ち玉の照合 | 10 秒ごとに API で実際の持ち玉を取り、記録と違ったら新規停止+警告 |
| 注文の照合 | 利確・損切りの注文が板に残っているか 10 秒ごとに確認。消えていたら置き直し、置き直せなければ成行で手仕舞い |
| 緊急停止 | ファイル `STOP` をリポジトリ直下に置いたら、全部成行で手仕舞いし新規を止める。画面にもボタン |
| 資金の下限 | 口座残高が開始時の 80% を下回ったら、全部手仕舞いして停止。再開はボスの指示 |

### 10.5 段階4の完了条件

- 28 日間、停止事故なしで動く。取引 20 回以上。
- 紙上運転の損益との差が説明できる(滑り・約定しなかった注文の数で)。説明できない差があれば報告し、ボスが続行か停止かを決める。

```
kaikai-bot/
  .github/workflows/collect.yml   ← 1時間ごとの収集(data 枝へ)
  docs/
    SPEC.md              ← この文書(正本)

  config/
    coins.yaml           ← 銘柄一覧(第1段階・第2段階)、HIP-3 かどうか
    costs.yaml           ← 手数料・滑り・資金調達料

  kaikai_bot/

    candles.py           ← 上位足の生成、欠損処理、除外日
    indicators.py        ← 指標の計算(第6章)
    strategy.py          ← 入り口・出口・安全装置の判断(第7章)。検証・紙上・本番で同じ関数を使う
    backtest.py          ← 中間報告・予備判定・正式判定・判定表・否決メモ(第8章)

## 16. 報告の形式

各段階・各判定の終わりに、次の順で書く。専門用語・関数名・ログの識別子は出さず、日本語で書く。

1. **結論**(1文): 段階 N は完了したか / 判定の結果はどうだったか
2. 完了条件または基準の充足(○×の表)
3. 数字: 試験の通過数、データの日数、判定表の要約(合格/不合格/判定不能/データ待ちの数)、紙上運転の要約
4. 自分で決めたこと(DESIGN_NOTES の見出しだけ)
5. 未解決・気になる点
6. 次に進む段階
